No, you can't safely share one connection pool across forked workers.

A pool holds live TCP sockets, and fork duplicates the file descriptors but not the protocol state. Two workers end up interleaving bytes on the same wire. Worker A sends a query, worker B sends another, and both read whichever response arrives first, so worker A's rows get returned to worker B.

You see "column does not exist" on a query that definitely has that column, or occasional unexpected message type errors from the driver.

Other things go wrong too. Whichever worker exits first tears down the socket and the others see connection reset. The parent thinks it holds n connections, but the operating system sees n times workers descriptors pointing at n sockets, and the server's max connections accounting disagrees with everyone.

The fix is to create the pool after the fork, sized so the total stays under budget. Use this sizing rule: per worker pool equals floor of max connections times 0.8 divided by worker count, then leave at least five connections free for superuser access and migrations.

With max connections at 100 and four workers, that's 20 each, round down to 18 so you have headroom when a worker is mid-restart and its old sockets haven't timed out yet.

One caveat: if you're behind PgBouncer in transaction mode, none of this applies the same way. The bouncer owns the real connections and your pool is just a set of cheap client-side handles. In that setup, oversizing the app pool is nearly free and max connections on Postgres itself can stay small, around 20 to 30.
