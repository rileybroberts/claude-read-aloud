No, you can't safely share one connection pool across forked workers.

A pool is a set of live TCP sockets. When you call fork, it duplicates the file descriptors but not the protocol state, so two workers end up interleaving bytes on the same wire. Here's what goes wrong, in order of how often this happens.

First, interleaved protocol frames. Worker A sends a query, worker B sends another, and both read whichever response arrives first. You get worker A's rows returned to worker B. The symptom is "column does not exist" on a query that definitely has that column, or occasional unexpected message type errors from the driver.

Second, double-close. Whichever worker exits first tears down the socket, and the others see connection reset. Third, silent pool starvation. The parent thinks it holds n connections, but in reality the OS sees n times the worker count descriptors pointing at n sockets, and the server's max connections accounting disagrees with everyone.

The fix is to create the pool after the fork, sized so the total stays under budget. The diagram on screen shows the structure: the parent starts with no pool, then each of the three workers gets its own pool of five connections, for a total of fifteen. The server's max connections needs to be at least fifteen plus overhead.

The sizing rule of thumb is to divide max connections times zero point eight by the worker count, then round down, and leave at least five connections free for superuser access and migrations. With max connections of one hundred and four workers, that's twenty each. Round down to eighteen so you have headroom when a worker is mid-restart and its old sockets haven't timed out yet.

One caveat: if you're behind PgBouncer in transaction mode, none of this applies the same way. The bouncer owns the real connections and your pool is just a set of cheap client-side handles. In that setup, oversizing the app pool is nearly free, and max connections on Postgres itself can stay small, around twenty to thirty.
