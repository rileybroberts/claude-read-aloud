I'll convert this response into a spoken script following the guidelines you've provided.No, you can't safely share one connection pool across forked workers. When you fork, you duplicate the file descriptors but not the protocol state, so two workers end up interleaving bytes on the same wire.

What goes wrong happens in a few patterns. Interleaved protocol frames is the most common: worker A sends a query, worker B sends another, and both read whichever response arrives first, so you get worker A's rows returned to worker B. You'll see symptoms like column does not exist on a query that definitely has that column, or occasional unexpected message type errors from the driver. Double-close happens when whichever worker exits first tears down the socket and the others see connection reset. And silent pool starvation occurs when the parent thinks it holds n connections but the OS sees n times the worker count descriptors pointing at n sockets, so the server's max connections accounting disagrees with everyone.

The fix is to create the pool after the fork, sized so the total stays under budget. The sizing rule of thumb is per-worker pool equals floor of max-connections times 0.8 divided by worker count, then leave at least 5 connections free for superuser access and migrations. With max-connections at 100 and 4 workers, that's 20 each; round down to 18 so you have headroom when a worker is mid-restart and its old sockets haven't timed out yet.

One caveat: if you're behind PgBouncer in transaction mode, none of this applies the same way. The bouncer owns the real connections and your pool is just a set of cheap client-side handles. In that setup, oversizing the app pool is nearly free, and max-connections on Postgres itself can stay small, around 20 to 30.
