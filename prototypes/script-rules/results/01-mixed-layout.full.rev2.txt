The core idea is to wait and retry when a request fails, doubling the wait each time with random jitter so clients don't retry all at once.

When a request fails with a transient error, you wait a bit and try again, doubling the wait each time so you stop hammering a struggling server. You add a little random jitter so a thundering herd of clients doesn't retry in lockstep. There's a compact implementation in the retry file under source lib. That code defines a with retry function that takes a callback and options for max attempts, base delay, and max delay. It tries the function up to five times by default, and for each failure it computes an exponential backoff capped at thirty thousand milliseconds, then adds up to thirty percent jitter before waiting. It only retries if the error is retryable, meaning a four twenty nine or five hundred status or higher, and it throws on the last attempt.

With the defaults, the delay schedule starts at two hundred fifty milliseconds for attempt one, then five hundred, one thousand, two thousand, and four thousand milliseconds for attempts two through five. When you add the maximum jitter, those become three twenty five, six fifty, one thousand three hundred, two thousand six hundred, and five thousand two hundred milliseconds. The cumulative wait by attempt five is just under five seconds.

There are a few things worth calling out before you ship this. First, don't retry non-idempotent writes unless the endpoint supports an idempotency key, because a retried post to a charges endpoint can double bill someone. Second, respect the retry after header. If the server tells you how long to wait, that header beats your computed backoff every time. Third, cap total elapsed time, not just attempt count, because five attempts with a thirty second ceiling can block a request for over a minute. And last, log the attempt number so retry storms are visible in your traces rather than hidden inside a single span.

To wire it up, there are four steps. Step one, install the helper and export it from your HTTP client module. Step two, wrap only the read paths first, that's get and head, and deploy. Step three, watch your p ninety nine latency and error rate dashboards for a day. Step four, then extend it to idempotent writes one endpoint at a time.

If retries still aren't enough, the next step up is a circuit breaker. After a threshold of consecutive failures, you stop calling the dependency entirely for a cooldown window and fail fast instead.
