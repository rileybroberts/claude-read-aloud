You can't safely share one connection pool across forked workers.

The problem is that a pool is a set of live TCP sockets, and when you call fork, it duplicates the file descriptors but not the protocol state. That means two workers end up interleaving bytes on the same wire. Here's what actually goes wrong, in order of how often it happens. First, interleaved protocol frames. Worker A sends a query, worker B sends another, and both read whichever response arrives first. You get worker A's rows returned to worker B. The symptom is an error saying column does not exist on a query that definitely has that column, or occasionally the driver reports unexpected message type. Second, double close. Whichever worker exits first tears down the socket and the others see connection reset. And last, silent pool starvation. The parent thinks it holds n connections, but in reality the OS sees n times workers descriptors pointing at n sockets, and the server's max connections accounting disagrees with everyone.

The fix is to create the pool after the fork, sized so the total stays under budget. The diagram shows a parent with no pool, forking three workers, each with a pool of 5, so max connections on the server needs to be at least 15 plus overhead. The sizing rule of thumb is per worker pool equals max connections times 0.8, divided by worker count, rounded down, then leave at least 5 connections free for superuser access and migrations. With max connections set to 100 and 4 workers, that's 20 each. Round down to 18 so you have headroom when a worker is mid restart and its old sockets haven't timed out yet.

One caveat. If you're behind PgBouncer in transaction mode, none of this applies the same way. The bouncer owns the real connections and your pool is just a set of cheap client side handles. In that setup, oversizing the app pool is nearly free, and max connections on Postgres itself can stay small, around 20 to 30.
