No, you can't safely share one connection pool across forked workers.

A pool is a set of live TCP sockets. When fork duplicates the file descriptors, it doesn't duplicate the protocol state, so two workers end up interleaving bytes on the same wire.

The first problem you'll hit is interleaved protocol frames. Worker A sends a query, worker B sends another, and both read whichever response arrives first. You get worker A's rows returned to worker B. The symptom might be "column does not exist" on a query that definitely has that column, or occasional unexpected message type errors from the driver.

Second, whichever worker exits first tears down the socket, and the others see a connection reset error. Third, the parent thinks it holds n connections, but in reality the OS sees n times the worker count descriptors pointing at n sockets, and the server's max connections accounting disagrees with everyone.

The fix is to create the pool after the fork, sized so the total stays under budget. The parent has no pool, then each worker creates its own pool with a share of the available connections. You want the total across all workers plus overhead to stay under the server's max connections limit.

Sizing rule of thumb: divide max connections times 0.8 by the worker count, then leave at least 5 connections free for superuser access and migrations. With max connections equal to 100 and 4 workers, that's 20 each. Round down to 18 so you have headroom when a worker is mid-restart and its old sockets haven't timed out yet.

One caveat: if you're behind PgBouncer in transaction mode, none of the above applies the same way. The bouncer owns the real connections and your pool is just a set of cheap client-side handles. In that setup, oversizing the app pool is nearly free, and max connections on Postgres itself can stay small, around 20 to 30.
