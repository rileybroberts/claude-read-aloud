You can't safely share one connection pool across forked workers.

A pool holds live TCP sockets. When you fork, the file descriptors are duplicated but the protocol state is not, so two workers end up interleaving bytes on the same wire. This causes several problems in practice. First, protocol frames get interleaved: worker A sends a query, worker B sends another, and both read whichever response arrives first, so you get the wrong worker's rows. You'll see errors like "column does not exist" on a query that definitely has that column, or unexpected message type errors from the driver. Second, whichever worker exits first tears down the socket and the others see connection reset. Third, the parent thinks it holds n connections, but in reality the OS sees n times the number of workers, and the server's connection accounting disagrees.

The fix is to create the pool after the fork, sized so the total stays under budget. Use the sizing rule: per-worker pool equals the floor of max connections times 0.8 divided by worker count, then leave at least 5 connections free for superuser access and migrations. With max connections of 100 and 4 workers, that's 20 each; round down to 18 to have headroom when a worker is mid-restart. If you're behind PgBouncer in transaction mode, this doesn't apply the same way because the bouncer owns the real connections and your pool is just client-side handles, so oversizing the app pool is nearly free.
