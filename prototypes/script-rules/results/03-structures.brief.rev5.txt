No, you can't safely share one connection pool across forked workers.

When you fork, the file descriptors get duplicated but the protocol state doesn't, so two workers end up sending bytes on the same wire. Worker A sends a query, worker B sends another, and both read whichever response arrives first. You get worker A's rows returned to worker B, which shows up as "column does not exist" on a query that definitely has that column, or occasional unexpected message type errors from the driver.

Whichever worker exits first tears down the socket, leaving the others with connection reset. The parent thinks it holds n connections, but the OS sees n times workers descriptors pointing at n sockets, and the server's accounting disagrees with everyone.

The fix is to create the pool after the fork, sized so the total stays under budget. Use this sizing rule: per worker pool equals floor of max connections times 0.8 divided by worker count, then leave at least 5 connections free for superuser access and migrations. With max connections of 100 and 4 workers, that's 20 each — round down to 18 so you have headroom when a worker is mid-restart and its old sockets haven't timed out yet.

One caveat: if you're behind PgBouncer in transaction mode, none of this applies the same way. The bouncer owns the real connections and your pool is just a set of cheap client-side handles, so oversizing the app pool is nearly free and max connections on Postgres itself can stay small, around 20 to 30.
