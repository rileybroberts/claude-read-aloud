That was a long one, so here's the one minute version.

Use uv for the daemon's Python runtime.

The comparison covers three options: uv, pipx, and a plain virtual environment using system Python. Install footprint first. uv is a single 40 megabyte Rust binary with a shared cache and can download its own CPython, no Python needed to start. pipx is small but needs Python and pip, usually via Homebrew which adds hundreds of megabytes if it's not present. Plain venv has no extra tooling, but the command line tools shim behind system Python is a 1 to 2 gigabyte install if never triggered, and it can pop a blocking GUI dialog. On latency, uv is fastest warm at 50 to 150 milliseconds for an already-synced script, cold around 5 to 15 seconds. pipx takes 15 to 40 seconds cold and nearly that warm because it re-resolves on install. Plain venv is 2 to 5 seconds to create, then 15 to 45 seconds for pip.

Reproducibility matters most. uv is strongest: a lock file pins the full dependency graph with hashes, cross-platform, plus the exact interpreter version. pipx is weak, it resolves from the index at install time with no pinning unless you ship a constraints file. Plain venv is weak by default, you can hand-write a pinned requirements file but the interpreter itself is whatever the OS shipped, currently Python 3.9.6 which is past end of life. For native wheels like MLX, uv works best because its managed interpreters are native arm64 builds with clean wheel tag resolution and parallel downloads. pipx is fine once the underlying Python is native arm64, which Homebrew's is. System Python is riskiest: Apple's Python 3 is a universal2 build where arch mismatches can trigger source builds that fail, or an x86 environment where MLX won't install at all, and 3.9 cuts you off from newer MLX releases.

The plain venv appeal is no dependencies, but on macOS that's an illusion. You depend on the command line tools shim, on an end-of-life Python 3.9, and on Apple's universal2 interpreter behaving with MLX's arm64 wheels, three things you don't control. Its failure mode is the only one that blocks on a modal dialog, which rules it out for something invoked from a hook. pipx is built to expose a CLI app on path for a human; your daemon is an implementation detail that teammates shouldn't see and you want pinned, not latest. pipx gives you neither locking nor interpreter management. uv's real cost is that it's a young, fast-moving third-party binary from a single vendor, a non-Python dependency in a Python project and a supply chain consideration. In exchange you get the only option that pins both interpreter and dependency graph, the only one with a fast warm path suitable for per-invocation startup, and the only one whose absence is a clean scriptable check.

The recommendation is uv, with the daemon declaring dependencies inline using PEP 723 and a committed lock file, plus a bootstrap that installs uv into a plugin-local prefix rather than mutating the teammate's shell config. The code shows a shell wrapper that installs uv into the plugin home on first run, then uses uv run with the locked flag to fail loudly instead of silently re-resolving. Two guardrails: pin the uv version you install so the bootstrap itself is reproducible, and set automatic Python downloads with an explicit minimum of Python 3.12 in the script header so MLX resolves against a native arm64 interpreter regardless of what's on the machine.
