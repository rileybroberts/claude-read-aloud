No, you can't safely share one connection pool across forked workers.

A pool is a set of live TCP sockets. When you fork, the file descriptors get duplicated, but the protocol state doesn't, so two workers end up interleaving bytes on the same wire. Here's what actually goes wrong, in order of how often I've seen it.

First, interleaved protocol frames. Worker A sends a query, worker B sends another, and both read whichever response arrives first. You get worker A's rows returned to worker B. The symptom is either a column does not exist error on a query that definitely has that column, or occasional unexpected message type errors from the driver.

Second, double-close. Whichever worker exits first tears down the socket, and the others see a connection reset error. Third, silent pool starvation. The parent thinks it holds n connections, but in reality the operating system sees n times the number of workers descriptors pointing at n sockets, and the server's max connections accounting disagrees with everyone.

The fix is to create the pool after the fork, sized so the total stays under budget. Instead of the parent holding a pool, each worker gets its own pool of five connections, and the server's max connections setting needs to account for the total across all workers.

The sizing rule of thumb is to take the floor of max connections times zero point eight, divided by worker count, then leave at least five connections free for superuser access and migrations. With max connections set to one hundred and four workers, that's twenty each. Round down to eighteen so you have headroom when a worker is mid-restart and its old sockets haven't timed out yet.

One caveat: if you're behind PgBouncer in transaction mode, none of the above applies the same way. The bouncer owns the real connections and your pool is just a set of cheap client-side handles. In that setup, oversizing the app pool is nearly free, and max connections on Postgres itself can stay small, around twenty to thirty.
