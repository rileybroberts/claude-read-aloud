I'll read this script aloud:Pipelines and subshells are both shell constructs that execute multiple commands, but they work in fundamentally different ways.

A pipeline chains commands together using the pipe operator. The output of one command flows directly into the input of the next. Each command runs in its own subprocess, and they execute concurrently. All the stages share the same overall environment because they're all children of the same parent shell, but changes to variables in one stage don't affect the others because each subprocess gets its own copy of the environment. As an example, you might pipe the output of cat into grep and then into wc to count matching lines.

A subshell creates an entirely new shell instance, either by wrapping commands in parentheses or by explicitly running bash with the c flag. It inherits the parent's environment when it starts, but it operates in complete isolation. Variable assignments, directory changes, and other state modifications all happen inside that subshell's memory space and vanish when the subshell exits. They never touch the parent shell at all. For example, you can change into a temporary directory, delete files there, and then back in the parent shell you're still in your original directory.

The key difference is concurrency and persistence. Pipeline stages run in parallel and pass data between each other. Subshells complete in sequence and don't share state. Pipelines use the pipe operator. Subshells use parentheses or a bash command invocation.

When it comes to exit status, a pipeline's exit code comes from the last command in the chain, or from any command if you enable pipefail. A subshell returns its own exit status to the parent. Both behave like subprocess calls in that their state changes don't leak back to the parent shell.

There are three gotchas you need to know. First, variables assigned in a pipeline stage disappear because the stage runs as a subprocess that can't modify the parent shell's memory. If you write cat data piped into a while loop that increments a counter, the counter is empty when the loop finishes. You can work around this by using process substitution with angle brackets or a here-string instead. Second, when a subshell calls exit with a code, it only terminates itself, not your entire script. Your parent shell continues running unless you explicitly check the question mark variable afterward. Third, the set e flag behaves differently in the two contexts. In a pipeline with set e enabled, only the rightmost command's failure will kill your script unless you also enable pipefail. In a subshell, set e applies to that subshell independently, so the subshell dies but the parent keeps going unless you propagate the exit code with the or-exit pattern.
