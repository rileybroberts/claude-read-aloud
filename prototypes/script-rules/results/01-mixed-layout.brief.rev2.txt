The idea is to wait after a failed request and try again, doubling the wait each time and adding random jitter so clients don't all retry at once.

The implementation goes in a retry file in the source lib folder. That file exports a function called with retry that takes a callback and options for max attempts, base delay, and max delay. The function loops through the attempts, catches errors, checks if they're retryable like a 429 or 500 status, calculates an exponential backoff capped at the max delay, adds up to 30 percent jitter, waits, and tries again. If the error isn't retryable or you've run out of attempts, it throws. The defaults give you five attempts starting at 250 milliseconds.

The table shows how the delays grow. The key thing is that by the fifth attempt you've waited just under 5 seconds total, and each step roughly doubles. Before you ship this there are four things to watch. Don't retry writes unless the endpoint has an idempotency key or you risk double charging. Respect the retry after header if the server sends one. Cap total elapsed time, not just attempt count, or five tries can block for over a minute. And log the attempt number so you can see retry storms in your traces.

To wire it up, first install the helper and export it from your HTTP client module. Then wrap only the read paths, GET and HEAD, and deploy. Watch your p ninety nine latency and error rate dashboards for a day. After that extend it to idempotent writes one endpoint at a time. If retries aren't enough the next step is a circuit breaker that stops calling the dependency entirely after a threshold of failures and fails fast during a cooldown window.
