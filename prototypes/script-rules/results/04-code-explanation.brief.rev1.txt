I'll rewrite this technical explanation as a spoken script for a colleague.Pipelines chain commands left to right where the output of one becomes the input of the next. Each command runs in its own process, but they all execute concurrently and share the parent shell's environment. Since each stage runs separately, variable changes in one don't affect the others.

A subshell creates an entirely new shell instance using parentheses or an explicit bash command. It inherits the parent shell's environment but runs independently. Any variable assignments or directory changes you make inside stay inside—when the subshell exits, the parent shell is completely unchanged.

So a pipeline uses the pipe operator and streams data between commands as they run in parallel. A subshell uses parentheses and isolates a whole sequence of commands from the parent. The key difference is that pipelines are about connecting data flow, while subshells are about creating a separate execution context.

There are three gotchas to watch for. First, pipeline variables disappear because the right side of the pipe runs in a subprocess that can't modify the parent's variables. If you need a loop to update a counter, use process substitution or a here-string instead. Second, a subshell can exit with a failure code but that doesn't stop your parent script—the parent keeps running unless you check the exit status afterward. Third, the set dash e flag behaves differently in pipelines versus subshells. In a pipeline with set dash e enabled, only the rightmost command's failure kills the script unless you also set pipefail. In a subshell, set dash e applies only inside that subshell, so it exits independently but your parent might not unless you explicitly propagate the exit code.
