# How a forked skill and a Stop hook reach the Response and an Engine

Research for [issue #3](https://github.com/rileybroberts/claude-read-aloud/issues/3). Date 2026-09-11, Claude Code 2.1.268 (`claude --version`). Sources are the official docs at `https://code.claude.com/docs/en/` (fetched as `.md` and grepped) plus `claude --help` and a read-only look at `~/.claude/settings.json` and `~/.claude/plugins/`. Vocabulary follows `CONTEXT.md` (Response, Script, Reading, Engine, Command, Auto mode).

**Headline.** A `context: fork` skill does *not* see the conversation, so the Command cannot read the Response from context. The Stop hook is the only place the Response is handed to us (`last_assistant_message`, and the docs name "read-aloud" as its intended use). So both Triggers should start from the Stop hook writing the Response to disk per session; the Command then injects that file into a forked skill with `` !`cmd` ``. Control subcommands can skip the model entirely via a `UserPromptExpansion` hook.

## a. `context: fork` skills

- **No conversation inheritance.** "Claude Code starts a new subagent of the type set in the `agent` field and gives it the skill content as its prompt. The subagent doesn't see your conversation history, so the skill's instructions have to stand on their own." And: "Despite the name, a skill with `context: fork` doesn't run in a fork of the current conversation ... When the task depends on that history, fork the conversation instead of using `context: fork`." https://code.claude.com/docs/en/skills#run-skills-in-a-subagent
- **A real conversation fork exists but is model-driven.** "A fork is a subagent that inherits the entire conversation so far ... only its final result comes back." It is started by Claude requesting the `fork` subagent type through the Agent tool, or by the user typing `/subtask <task>`; no frontmatter makes a skill run as a conversation fork. https://code.claude.com/docs/en/sub-agents#fork-the-current-conversation
- **What the forked skill does get:** SKILL.md content as its task, the agent type's system prompt, and CLAUDE.md "except when the agent is Explore or Plan". The rendered content includes `` !`cmd` `` output and `$ARGUMENTS`, so anything a shell command can read is available to the fork. https://code.claude.com/docs/en/skills#run-skills-in-a-subagent
- **`agent`**: "Which subagent type to use when `context: fork` is set." Built-ins or any custom subagent (plugins can ship one under `agents/`); default `general-purpose`. "For security reasons, plugin subagents don't support the `hooks`, `mcpServers`, or `permissionMode` frontmatter fields"; a subagent otherwise "inherits the main conversation's mode", and under `auto` mode the classifier evaluates its tool calls. https://code.claude.com/docs/en/skills#frontmatter-reference , https://code.claude.com/docs/en/sub-agents#choose-the-subagent-scope , https://code.claude.com/docs/en/sub-agents#permission-modes
- **`background`**: default `true` since v2.1.218; "its result arrives in your conversation when it completes. Set `background: false` in the frontmatter to instead wait for the result in the turn that invoked the skill." Claude Code waits anyway in `-p` mode, with `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, or "when you invoke a forked skill while an earlier invocation of the same skill is still running". "A backgrounded fork also runs with the narrower tool set that applies to background subagents." https://code.claude.com/docs/en/skills#run-skills-in-a-subagent
- **`allowed-tools`**: "grants permission for the listed tools during the turn that invokes the skill ... It does not restrict which tools are available". Also the only way to keep an injected `` !`cmd` `` from aborting on a permission check. Not gated by workspace trust. https://code.claude.com/docs/en/skills#pre-approve-tools-for-a-skill In a plugin skill, `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PLUGIN_DATA}` are substituted in both the markdown and the `allowed-tools` Bash rules: "Using the same variable in both places lets a skill run a bundled script without a permission prompt." https://code.claude.com/docs/en/skills#available-string-substitutions
- **`model` / `effort`**: `model` "Accepts the same values as `/model`, or `inherit`"; "With `context: fork`, the value sets the forked subagent's model instead." `effort` takes `low|medium|high|xhigh|max`. https://code.claude.com/docs/en/skills#frontmatter-reference
- **How the result returns; can it be silenced?** "A background subagent's results reach Claude as a completion notification in a later turn. Claude waits for that notification before reporting the subagent's results". Only the fork's final message comes back; its tool calls stay out of the main context. Nothing documented suppresses the return; the smallest footprint is a fork whose final message is one short line, which the main model then relays in its own (small) turn. The fork's panel row disappears on success and a `/tasks to see subagents` footer hint shows for 30 s. https://code.claude.com/docs/en/sub-agents#run-subagents-in-foreground-or-background

## b. Cheapest `/read-aloud stop` and `/read-aloud auto on|off`

- **A skill is always a model turn.** "When you or Claude invoke a skill, the rendered `SKILL.md` content enters the conversation as a single message and stays there across later turns." https://code.claude.com/docs/en/skills#skill-content-lifecycle
- **`` !`cmd` `` runs first and can do the real work.** "runs shell commands before the skill content is sent to Claude. The command output replaces the placeholder". It runs "through the Bash tool", in the session cwd, under the Bash tool's 2-minute timeout, stderr merged into stdout; non-zero exit "aborts the entire skill invocation"; "Injected commands never prompt for permission. When a command's permission check returns anything other than allow, Claude Code aborts", so pre-approve with `allowed-tools`. https://code.claude.com/docs/en/skills#inject-dynamic-context and https://code.claude.com/docs/en/skills#how-injected-commands-run
- **Making the model turn trivial.** `model: haiku` + `effort: low` apply "for the rest of the current turn"; `disable-model-invocation: true` keeps the description out of context and stops Claude auto-invoking; `$ARGUMENTS`, `$0`, `$1` route `/read-aloud stop` and `/read-aloud auto on` into one SKILL.md; `argument-hint` shows in autocomplete. `${CLAUDE_SESSION_ID}` is a documented content substitution: "The current session ID. Useful for logging, creating session-specific files, or correlating skill output with sessions." Caveat: a teammate with `"disableSkillShellExecution": true` gets every `` !`cmd` `` replaced with a placeholder. https://code.claude.com/docs/en/skills#frontmatter-reference , https://code.claude.com/docs/en/skills#available-string-substitutions , https://code.claude.com/docs/en/skills#inject-dynamic-context
- **A no-model-turn path exists: the `UserPromptExpansion` hook.** "Runs when a user-typed command expands into a prompt before reaching Claude ... Matches on `command_name`." Input includes `command_name`, `command_args`, `command_source`, `prompt`, plus `session_id`. Decision: "`decision: "block"` prevents the command from expanding"; "`reason`: Shown to the user when `decision` is `"block"`"; exit 2 with stderr does the same. A plugin hook matching `read-aloud` can run `read-aloud-ctl stop` when `command_args` is a control verb and block with a one-line `reason`; the skill never expands and no model call happens. It "covers the path `PreToolUse` doesn't": typing `/skillname` directly. https://code.claude.com/docs/en/hooks#userpromptexpansion
- No other documented mechanism runs a shell command from a slash command without a model turn; keybindings cannot (map, Facts).

## c. The `Stop` hook

- **When it fires.** "Runs when the main Claude Code agent has finished responding. Does not run if the stoppage occurred due to a user interrupt. API errors fire StopFailure instead." It is per turn: the end of the turn, after any tool calls. Subagent completions fire `SubagentStop`, not `Stop`. https://code.claude.com/docs/en/hooks#stop and https://code.claude.com/docs/en/hooks#subagentstop
- **`last_assistant_message` is the Response.** "contains the text content of Claude's final response, so hooks can access it without parsing the transcript file. For hooks that act on the just-completed turn, such as read-aloud or notification hooks, use this field rather than reading `transcript_path`: the transcript file isn't guaranteed to include the final message at Stop time on all versions." https://code.claude.com/docs/en/hooks#stop-input
- **Full Stop input:** common fields `session_id`, `prompt_id`, `transcript_path`, `cwd`, `scratchpad_dir`, `permission_mode`, `effort`, `hook_event_name`; Stop-specific `stop_hook_active`, `last_assistant_message`, `background_tasks`, `session_crons`. https://code.claude.com/docs/en/hooks#common-input-fields
- **Per-session state is possible.** `session_id` is in every hook input, and `CLAUDE_CODE_SESSION_ID` is "Set automatically to the current session ID in Bash and PowerShell tool subprocesses, hook command subprocesses ... this matches the `session_id` field in the hook JSON input and is updated on `/clear`." Note the two spellings: the env var is `CLAUDE_CODE_SESSION_ID`; the skill-content substitution is `${CLAUDE_SESSION_ID}`. https://code.claude.com/docs/en/env-vars
- **`async: true`.** "runs in the background while Claude continues working. Async hooks can't block or control Claude's behavior". "Once an async hook is running in the background, Claude Code doesn't enforce `timeout` on it." Its `additionalContext`/`systemMessage` are delivered to Claude on the next turn and "neither field is shown to you"; "Async hook completion notifications are suppressed by default." In `-p` mode async hooks still running are killed at teardown: "If your hook's work must outlive a `claude -p` session, start a fully detached process from it." https://code.claude.com/docs/en/hooks#run-hooks-in-the-background
- **`asyncRewake`.** "runs in the background and wakes Claude on exit code 2. The hook's stderr, or stdout if stderr is empty, is shown to Claude as a system reminder"; timeout is enforced. Not wanted here (it would inject into the conversation). https://code.claude.com/docs/en/hooks#command-hook-fields
- **Timeout.** Default 600 s for `command` hooks (30 s for `prompt`, 60 s for `agent`); lowered to 30 only on `UserPromptSubmit`/`PreModelSwitch`/`PostModelSwitch` and 10 on `MessageDisplay`. https://code.claude.com/docs/en/hooks#common-fields
- **Quietest success.** Exit 0 with empty stdout: "For most events, Claude Code writes stdout to the debug log and doesn't show it in the transcript"; stderr on exit 0 "goes to the debug log only". `suppressOutput` "Has no effect". `systemMessage` is a "Warning message shown to the user" (sync hooks only). `terminalSequence` can ring the bell or post a desktop notification. Exit 2 or `decision: block` makes Claude continue (loop-capped at 8, `stop_hook_active` flags the re-entry), so never use them here. https://code.claude.com/docs/en/hooks#exit-code-0 and https://code.claude.com/docs/en/hooks#json-output
- **Reading a config file.** "A hook process inherits the parent environment"; "Handlers run in the current directory with Claude Code's environment"; hooks run without a controlling terminal; and "Hook commands themselves run unsandboxed." Plugin hooks also get `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}` and `CLAUDE_PLUGIN_OPTION_<KEY>`. So the script can `jq` a JSON file under `~/.claude/read-aloud/` keyed by `session_id` on every turn; there is no hook-side caching to defeat. https://code.claude.com/docs/en/hooks#common-input-fields , https://code.claude.com/docs/en/hooks#directoryadded , https://code.claude.com/docs/en/hooks#reference-scripts-by-path
- **Configuration is static per session.** The `/hooks` menu is read-only; hooks come from settings files or the plugin's `hooks/hooks.json` ("When a plugin is enabled, its hooks merge with your user and project hooks"). Toggling Auto mode must therefore be a config-file flag the hook reads, not hook registration. https://code.claude.com/docs/en/hooks#the-hooks-menu

## d. Talking to a long-lived local daemon

- **Hooks are the safest launch point.** They run unsandboxed with the user's environment (see c). Child-process lifetime for interactive sessions is not documented; the only statement is the `-p` teardown kill and the advice to "start a fully detached process". Treat `setsid nohup daemon </dev/null >log 2>&1 &` (or a launchd agent) as the pattern and verify it (Unsettled 4). https://code.claude.com/docs/en/hooks#run-hooks-in-the-background
- **Bash tool background lifetime.** "A command that a foreground subagent started stops when that subagent gives its final response. A command that the main conversation or a background subagent started keeps running after a final response." A background forked skill may leave a process running; `run_in_background` is the documented way. https://code.claude.com/docs/en/tools-reference#background-commands
- **Sandbox is off by default** (`sandbox.enabled` default `false`); this machine has no `sandbox` key. If a teammate turns it on: on macOS the sandbox "blocks every Unix socket" unless listed in `sandbox.network.allowUnixSockets`; `allowLocalBinding` (default `false`) is needed to bind localhost; outbound "pre-allows no domains by default" and prompts; "Bash commands inside a subagent are sandboxed when sandboxing is enabled in the parent session"; `excludedCommands` runs named commands outside the sandbox. `` !`cmd` `` goes through the Bash tool so it is sandboxed too; hooks are not. https://code.claude.com/docs/en/settings-reference#sandbox-enabled , https://code.claude.com/docs/en/settings-reference#sandbox-network-allowunixsockets , https://code.claude.com/docs/en/sandboxing#network-isolation , https://code.claude.com/docs/en/sandboxing#limitations
- **Permissions for `Bash(...)`.** Rules match the whole command with `*` as wildcard; `Bash(read-aloud-ctl *)` also matches the bare command; `:*` is equivalent; each `&&`/`|`/`;` subcommand must match independently. Skill `allowed-tools` grants for the invoking turn; settings `permissions.allow` grants for the session. A plugin's own `settings.json` supports only `agent` and `subagentStatusLine`, so a plugin cannot ship allow rules; skill `allowed-tools` is the vehicle. https://code.claude.com/docs/en/permissions#wildcard-patterns and https://code.claude.com/docs/en/plugins-reference#file-locations-reference
- **Session-wide env for the socket path.** `CLAUDE_ENV_FILE` lets a `SessionStart` hook `export` variables for later Bash commands; it is "available for SessionStart, Setup, CwdChanged, and FileChanged hooks" only. https://code.claude.com/docs/en/hooks#persist-environment-variables
- **Unix socket vs CLI.** Docs are neutral. A CLI wrapper (`read-aloud-ctl`) that speaks to the daemon over a unix socket keeps every caller (Stop hook, `UserPromptExpansion` hook, `` !`cmd` ``, the fork's Bash) on one permission pattern and one sandbox exemption list.
- **A nested `claude -p` from a hook** (for the Auto-mode Script writer) is a child session: `CLAUDECODE=1` and `CLAUDE_CODE_CHILD_SESSION=1` are set; `--bare` skips hooks (so our own Stop hook does not recurse) and `--no-session-persistence` keeps it out of `/resume`; Bedrock credentials "use their own credentials" under `--bare`. `claude --help`, https://code.claude.com/docs/en/env-vars

## e. Plugin `userConfig` and `${user_config.x}`

- **Schema.** `type` (`string|number|boolean|directory|file`), `title`, `description` required; `sensitive`, `required`, `default`, `multiple`, `min`/`max` optional. Prompted "when the plugin is enabled"; settable non-interactively with `claude plugin install --config key=value`. https://code.claude.com/docs/en/plugins-reference#user-configuration
- **Where it can be read.** "available for substitution as `${user_config.KEY}` in MCP and LSP server configs and hook commands. Non-sensitive values can also be substituted in skill and agent content. All values are exported to hook processes as `CLAUDE_PLUGIN_OPTION_<KEY>`". But "Fields that run in a shell reject `${user_config.*}`": shell-form hook commands fail; use exec form (`args`) or read the env var. Monitor commands must "Read the value from a config file". https://code.claude.com/docs/en/plugins-reference#user-configuration
- **Where it is stored.** Non-sensitive: `pluginConfigs[<plugin-id>].options` in `~/.claude/settings.json`; sensitive: macOS Keychain, falling back to `~/.claude/.credentials.json`. Read only from user settings, `--settings`, and managed settings; project `.claude/settings*.json` entries are ignored. https://code.claude.com/docs/en/settings-reference#pluginconfigs
- **Persistent plugin state.** `${CLAUDE_PLUGIN_DATA}` "resolves to `~/.claude/plugins/data/{id}/`" and "survives plugin updates"; `${CLAUDE_PLUGIN_ROOT}` "Changes on each plugin update". Locally `~/.claude/plugins/data/` already holds per-plugin dirs. https://code.claude.com/docs/en/plugins-reference#persistent-data-directory

## Recommended mechanics

1. **Stop hook captures the Response, every turn.** Plugin `hooks/hooks.json`, `Stop`, exec form (`command` + `args: []`), a script under `${CLAUDE_PLUGIN_ROOT}`. First, synchronously and fast, write `last_assistant_message` to `~/.claude/read-aloud/sessions/<session_id>/response.md` via temp file + rename (this is what the Command reads next turn). Then, if `config.json` (global `auto`, optional `sessions/<id>.json` override) says Auto mode is on and the word count clears the threshold, hand off and exit 0 with empty stdout. Nothing prints. Keep the hook synchronous (the write is milliseconds) or make the handoff a fully detached child; do not rely on `async: true` for the file write because the user may type `/read-aloud` immediately.
2. **Auto mode Script writer runs outside the conversation.** The handoff is `read-aloud-ctl auto-read --session <id>`, which asks the daemon to run `claude -p --bare --no-session-persistence --model <small> --effort low` with the Script style prompt and the Response on stdin, streaming paragraphs to the Engine. `--bare` prevents recursion into our own Stop hook. The main conversation never sees the Script.
3. **The Command is a forked skill fed by the saved Response.** `/read-aloud [brief] [--show]`: `context: fork`, `agent: read-aloud-writer` (plugin agent with `tools: Bash` and a small `model`; it cannot set `permissionMode`, so the skill's `allowed-tools` grant and the session's permission mode govern its Bash calls), `background: true`, `disable-model-invocation: true`, `allowed-tools: Bash(${CLAUDE_PLUGIN_ROOT}/bin/read-aloud-ctl *)`. Body starts with `` !`${CLAUDE_PLUGIN_ROOT}/bin/read-aloud-ctl response --session ${CLAUDE_SESSION_ID}` `` (both placeholders are documented substitutions; the injected command runs in the main session's Bash tool before the fork spawns), then instructs the writer to emit the Script paragraph by paragraph through `read-aloud-ctl say --session ...` and finish with one fixed line, e.g. `Reading started.` The main model relays that line; the Stop hook treats a Response equal to that sentinel (or under the threshold) as not readable, so the relay does not trigger Auto mode.
4. **Control verbs never reach the model.** `UserPromptExpansion` hook with matcher `read-aloud`: if `command_args` starts with `stop`, `auto`, `status`, or `config`, run `read-aloud-ctl <args>` and print `{"decision":"block","reason":"<one line>"}`; otherwise exit 0 so the skill expands. Fallback if the block rendering is unacceptable: a second tiny skill with `` !`read-aloud-ctl $ARGUMENTS` ``, `model: haiku`, `effort: low`.
5. **One CLI, one daemon, one socket.** `read-aloud-ctl` (Python via `uv`, or a thin shell wrapper) talks to the daemon over `~/.claude/read-aloud/daemon.sock`, auto-starting it detached when absent; a `SessionStart` hook may pre-warm it and `export READ_ALOUD_SOCK=...` via `CLAUDE_ENV_FILE`. Document for sandboxed teammates: `sandbox.network.allowUnixSockets` for the socket or `excludedCommands: ["read-aloud-ctl *"]`.
6. **Config.** Install-time answers via `userConfig` (voice, default threshold, duration cap), exported to hooks as `CLAUDE_PLUGIN_OPTION_*` and copied into `~/.claude/read-aloud/config.json` on first run; runtime toggles (Auto mode on/off per session) live only in that JSON, edited by `read-aloud-ctl`, because hooks cannot be re-registered mid-session and `pluginConfigs` has no documented runtime write path.

## Unsettled: a prototype must test

1. Whether the env var `CLAUDE_CODE_SESSION_ID` inside a forked subagent's Bash tool carries the main session's ID (subagents "run in the same process as the parent session", but the docs do not say). The `` !`cmd` `` path is covered by the documented `${CLAUDE_SESSION_ID}` substitution, so the skill should pass the ID explicitly to the writer rather than rely on the fork's environment.
2. How a `UserPromptExpansion` block renders (`reason` as a plain notice or an error banner) and whether anything lands in the transcript or context.
3. Whether the main-session turn that relays a forked skill's completion fires `Stop` (expected yes) and whether the sentinel/threshold check reliably keeps Auto mode quiet on it.
4. Detached-process survival: does a `setsid nohup ... &` child of a synchronous Stop hook outlive the hook and the interactive session on macOS, or is a launchd agent required.
5. Whether an `allowed-tools` rule of the form `Bash(${CLAUDE_PLUGIN_ROOT}/bin/read-aloud-ctl *)` still matches when the fork's writer calls the CLI through `uv run` or with a leading `VAR=` assignment, and whether the grant survives into the background fork's turn (the grant is documented as lasting "the turn that invokes the skill").
6. Under `sandbox.enabled: true`, whether a localhost TCP connect from a sandboxed command counts as a domain needing approval, and whether `~` expands in `allowUnixSockets`.
7. Exact on-screen footprint of a background forked skill: what the main model prints when relaying `Reading started.`, and whether the 30-second `/tasks` footer hint is acceptable as the "one-line notice".
8. Latency and cost of `claude -p --bare --model <small>` launched from the daemon on this Bedrock setup, against the 5-second first-audio target; whether streaming paragraphs from `-p` output (`--output-format stream-json`) is practical.
9. Whether `${user_config.KEY}` substitution in skill content happens before `` !`cmd` `` executes (it is documented for content, not for injected commands).
10. Race between the Stop hook's file write and the user's next `/read-aloud`: confirm a synchronous hook completes before the prompt is accepted, and measure its cost per turn.
